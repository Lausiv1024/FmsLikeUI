# 設計ノート

実装した結果として確定した設計と、その理由。迷ったところと、あえて Flutter と違えたところを残します。

## 3層と、その責任分担

```
  Widget          使い捨て / 毎フレーム作り直す / アリーナ確保
    │             「こう見えてほしい」という記述でしかない
    │  createElement()
    ▼
  Element         永続 / 型 + Key で差分検出 / State を保持
    │             ここが同一性(identity)の担い手
    │  createRenderObject() / updateRenderObject()
    ▼
  RenderObject    永続 / BoxConstraints でレイアウト / LVGL へ描画
    │             値が実際に変わったときだけ LVGL を触る
    ▼
  lv_obj_t        フラットな1階層。絶対座標。描く葉ノードだけが持つ
```

**LVGL のレイアウト機能(flex / grid)は使っていません。** 自前のレイアウトが出した絶対座標を
`lv_obj_set_pos` / `lv_obj_set_size` に流し込むだけです。LVGL に任せているのは、
描画・フォントラスタライズ・dirty area 管理・タッチのヒットテストだけです。

### lv_obj を持つのは「実際にピクセルを出すもの」だけ

`Column` / `Row` / `Padding` / `Align` / `Expanded` はレイアウト専用の RenderObject で、
LVGL オブジェクトを 1 つも作りません。M1 デモの実測は **Widget 88 個 → lv_obj 34 個**で、
LVGL 側のツリーは実際に 1/3 以下に収まっています。

`lv_obj` はすべて 1 つのルートの直接の子で、座標は絶対値です。ツリーがどれだけ深くなっても
LVGL 側は浅いままで、z 順は描画順(= 深さ優先の走査順)に一致します。走査中に連番の子インデックスを
振ることでこれを保証していて、これが `Stack` の後ろの子が手前に来る仕組みです。

## Widget のメモリ:バンプアリーナ

Flutter の Widget は GC 前提の使い捨てオブジェクトです。C++ でこれを素直にやるために、
**`Widget::operator new` をアリーナに差し替えて**います。`build()` の中の `new Column{...}` は
ポインタを進めるだけで、ヒープを触りません。

デストラクタは走ります(Widget は `std::function` を持つため)。アリーナは確保したオブジェクトを
記録しておき、`reset()` で構築の逆順に仮想デストラクタを呼びます。登録は `operator new` ではなく
**Widget のコンストラクタ**で行います — その時点で vtable が入っているので、後で仮想ディスパッチが効きます。

アリーナは **2 面あって交互に使います**。あるパスが片方を埋めている間、前のパスの Widget はもう片方に
無傷で残っています。これによって、前フレームに捕まえたコールバックや `State::widget()` が、
次の次のビルドまで安全に生きています。

## あえて Flutter と違えた点:再ビルドの粒度

**何かが dirty になったら、木全体を作り直します。** dirty なサブツリーだけではありません。

これはアリーナと引き換えの選択です。サブツリーだけを再ビルドすると、再ビルドされなかった Element は
古いアリーナの Widget を指したまま残り、そのアリーナを次に使い回した瞬間に宙吊りになります。
`Element` に Widget のコピーを持たせれば回避できますが、全 Widget に `clone()` を実装する
ボイラープレートに見合いません。

**代償はほとんどありません。** 数百個の Widget の再ビルドはポインタ加算と仮想呼び出しが数百回です。
高くつく部分 —— LVGL への差分書き込みと、LVGL 自身の dirty area 再描画 —— は
インクリメンタルなままです。RenderObject は**値が実際に変わったときしか LVGL を触らない**からです。

つまり **「全部作り直す」は「全部描き直す」を意味しません。** ここが設計の要です。

### 実機の実測

| 画面 | Widget | lv_obj | 再ビルド(実機) |
|---|---|---|---|
| M1/M2 デモ | 89 | 34 | 1.1 〜 2.5 ms |
| M3 カタログ | 363 | 122 | 4.1 〜 5.0 ms |
| M4 FMS 2画面 | 902 | 282 | **11 ms** |

30fps のフレーム予算 33ms に対して、902 個の Widget を全部作り直して 11ms(33%)。
Widget 1 個あたり約 12µs で、3 つの画面すべてで一貫しています。

**スケール限界は見えています。** Widget 1 個あたり約 12µs なので、1 ページが 1500 個を超えるあたりで
20ms に達し、予算を圧迫し始めます。FMS のページはそこまで大きくならない想定ですが、もしそうなったら
Element に Widget のコピーを所有させて dirty サブツリーだけ再ビルドする方向へ、閉じた変更で移行できます
(全 Widget に `clone()` を実装するボイラープレートが対価)。

いま最適化しないのは、**その必要が無いことを実機の数字が示しているから**です。

## 触れないもの / まだ無いもの

- **クリッピングとスクロール**: `lv_obj` がフラットなので、クリップは今のところ効きません。
  実機の FMS にスクロールする画面が無いこと、そして後述の**窓送り**がその代わりになることが
  分かったので、入れていません。必要になったら、クリップ境界の RenderObject だけ
  `lv_obj` を作って子をその下にぶら下げる(= フラット構造に局所的な例外を入れる)のが素直です。
  → [長いリストは窓で送る](#長いリストは窓で送るスクロールしない)
- **アニメーション**: FMS はほぼ静的なので後回し。入れるなら `lv_anim` のラッパではなく、
  `AnimationController` + `setState` の形にするのが API の一貫性として正しい。
- **親をまたぐ Element の再利用**: キー付き再配置(下記)が効くのは**同じ親の中だけ**です。
  別の親へ移した Widget は、キーが同じでも作り直されます。これを可能にするには Flutter の
  `GlobalKey` と、ツリー全体で共有する inactive Element リストが要る —— つまり BuildOwner が
  ツリー横断の状態を持つことになります。リストの並べ替えはすべて同一の親の中で起きるので、
  その対価を払う理由がまだありません。
(InheritedWidget / Theme は M2 で入りました。下記参照。)

## キー付き再配置

子リストの突合は、位置合わせだけでは足りません。`[A, B, C]` を `[C, A, B]` に並べ替えると、
スロット単位の比較ではどのスロットもキーが一致せず、**State も RenderObject も lv_obj も全部
捨てて作り直す**ことになります。「動いた」というだけの理由で。

そこで Flutter と同じ 4 段構えにしています(`Element::updateChildren`):

1. 先頭から一致する限りその場で更新し、最初の不一致で止まる
2. 末尾から一致する限り**数える**(位置は中間が確定するまで決まらない)
3. 残った中間のうち**キーを持つ子をプールに退避**。キーの無い子は移動後に同定しようがないので破棄
4. 新しい中間を順に埋める。キーが一致する子がプールにいれば、その Element を**新しい位置で引き取る**

引き取られた Element は親も owner も変わらないので、再 mount も `initState` も `dispose` も
走りません。新しい Widget を受け取るだけ —— それが State が生き残るということです。

**この設計で一番重要なのは 1 と 2 です。** 我々は毎フレーム全ツリーを再ビルドするので、
`syncChildren` は全 Row / Column で毎フレーム走ります。ここに毎フレームのアロケーションを
持ち込めば確実に遅くなる。値だけが変わって形の変わらないリスト —— FMS のページのほぼ全部 ——
は 1 で丸ごと食い切られ、**プールにもスクラッチにも触れずに返ります**。作業用バッファは
`kids_` と同じく使い回すので、形が変わるリストでもウォームアップ後は malloc しません。

`std::unordered_map` を使っていないのも同じ理由です。中間はせいぜい数十要素で、その規模なら
連続メモリの線形探索のほうが速く、しかも確保しません。バッファを Element ごとに持つのは
**突合が再帰的**だからです: 外側の Row のプールが生きている最中に、子の更新が内側の Row の
突合を走らせます。ファイルスコープの共有バッファでは内側が外側を壊します。

デモで見られます。`--demo reorder` の KEYS を切り替えると、キーがあるときは行に打たれた通し番号が
行と一緒に動き(`lv_created` は 0 のまま)、キーが無いときは番号がその場に留まって
データだけが横をすり抜けていきます。

**コストは再突合ではなく LVGL 側にあります。** `--rows 40`(lv_obj 301 個 = 実機ページ相当)で
測ると、build は並べ替えの規模に関わらず 95〜125µs で一定なのに、paint は並べ替えなしの 110µs から
全反転で 3.6ms まで跳ねます。フラットな lv_obj ツリーで index を動かす `lv_obj_move_to_index` の
代償で、リストが長くなるとオブジェクト数より速く増えます。隣接 1 つの入れ替えなら 190µs で
実質ただなので、実際の FMS 操作では問題になりません。

実機で測ると、コストは **z 順を付け替えた lv_obj の数**でほぼ決まります(`FrameStats::lv_moved`)。
1 個あたりおよそ 0.5ms:

```
実機の paint ≒ 2.3ms + 0.5ms × lv_moved
```

33ms の予算に収まるのは 1 フレーム 60 個前後まで。ウェイポイントを 1 つ上下に動かすのは
`lv_moved=7` で **6.4ms、余裕で内側**です。リスト全体の並べ替えは `lv_moved=273` で
**127.6ms、予算の約 4 倍** —— **この構造では成立しません**。実際の FMS 操作は前者なので、
キー付き再配置は実用上安全です。内訳は [PERF.md](PERF.md) にあります。

## 長いリストは窓で送る(スクロールしない)

実機の F-PLN ページにはスクロールバーもフリックもありません。**行数は固定**で、上下の矢印が
その窓をフライトプランの上を 1 ウェイポイントずつ歩かせます。これを真似たのは見た目のためでは
なく、**このフレームワークではそちらのほうが構造的に安い**からです。

描画する RenderObject は漏れなく `lv_obj` を 1 つ持ちます。つまりスクロールビューは、N 件の
リストに対して `lv_obj` を N 個実体化することになる —— それを避けるには画面外を作らない
仮想化層が要り、クリップも要る。窓送りなら、リストが何件になろうと**常に窓の行数 W 個**です。

### 型は 3 つ

```cpp
FmsWindowPos pos;          // count / window / first / step。ただの値
pos.count = 24; pos.window = 8; pos.step = 1;

new FmsWindow{{ .pos = pos, .row = [](int index, int slot) { ... } }};
new FmsPager{{  .pos = pos, .on_prev = ..., .on_next = ... }};
```

`FmsWindowPos` はページの State が 1 つ持ち、`FmsWindow` と `FmsPager` の**両方に渡します**。
分けてあるのは意図的で、次の規則のためです。

### 矢印は、自分が送る領域の外に置く

送る対象がリストだけなら矢印はリストのヘッダ行(実機では FACT の行)に置けます。
`ACTIVE/F-PLN` より下**全部**を送るなら、矢印は自分自身も送られてしまうので、
その外 —— MSG LIST の並ぶフッタ右 —— に出すしかありません。**配置はスコープが決めます。**

`FmsScaffold` の `footer` は `WidgetList` をそのまま Row に流すので、フッタ配置は
`new Spacer{}` の後に `FmsPager` を置くだけで、フレームワーク側の変更は要りません。
`--demo fplan` の ARROWS ボタンで両方を切り替えられます。

### 行にキーを打ってはいけない

ここが唯一の落とし穴です。「リストなんだから行にキーを」と考えるのは自然ですが、**窓送りでは
逆効果**です。

キーは Element を**ウェイポイント**に結びつけます。窓を 1 つ進めると、上から外れた行は破棄され、
下に現れた行が作られる。キーが無ければ行は**スロット同士**で突合され、変わるのは文字列だけです。

`--demo fplan` の 1 ステップあたり、実機(Tab5)実測:

| | `lv_created` | `lv_moved` | total | 33ms 予算比 |
|---|---|---|---|---|
| キー無し(既定) | **0** | **0** | **11.8ms** | 36% |
| キー有り | 7 | 7 | **29.8ms** | **90%** |
| キー有り、1 ページ送り | 49 | 49 | **98.1ms** | **297%** |

シミュレータでは 0.8ms 対 2.3ms で、**どちらも「速い」で終わってしまいます**。
この判断が意味を持つのは実機だけでした。キー有りは 1 ステップで予算の 9 割を使います。

なお **キー無しの 11.8ms は下限ではありません**。生成も移動も 0 ですが、ラベル 47 個が
書き換わっており、1 個あたり実機で約 0.18ms かかります。`lv_created` も `lv_moved` も 0 のまま
paint が 9.2ms になる —— この見えないコストを数えるために `FrameStats::lv_retexted` があります。

47 は「8 行 × 7 セル = 56」ではありません。隣の行と同じセルは比較されて飛ばされます。
**画面の行数から導出せず、カウンタを読んでください** —— 56 と書いていたのを、カウンタを
入れた最初の実行が訂正しました。詳細は [PERF.md](PERF.md#実機で測った)。

キー有りでも 7 で済んでいるのは、**全行の `lv_obj` 数が同じ**だからです。生き残った行は元の
index をそのまま保てる。1 行だけ項目の多い行を混ぜれば、それ以降の index が全部ずれて
`lv_moved` は跳ね、[キー付き再配置](#キー付き再配置)で測った 1 個 0.5ms の世界に入ります。

**キーは並べ替えられるリストのための道具です。** 窓の中のリストは並べ替えられません、
覗かれるだけです。

### 末尾の空行は消さない

窓がリストの末尾からはみ出した分は、行を**減らさず**にダッシュで埋めます(`pos.at(slot)` が
`-1` を返す)。行が減るとツリーの形が変わり、reconciler は文字列が変わっただけの操作に対して
`lv_obj` の破棄と生成をやることになります。実機の画面が空行をダッシュで描くのと同じ理由で、
「行が無い」と「行が空」は別の意味でもあります。

## 他のタスクから UI を更新する

センサ、CAN、ネットワーク受信 —— 実アプリのデータは UI タスクの外から来ます。ここには
**踏むと無言で壊れる罠**があるので、規約を先に決めてあります。

### 規約

**`setState()` はフレームループのスレッドからしか呼べません。** 他タスクからは:

```cpp
// 単一の受信タスク
altitude_.store(v, std::memory_order_relaxed);   // 置き場はアプリが持つ
FmsApp::instance().requestFrame();               // そのあとで、これ
```

`build()` は `altitude_.load()` を読みます。順序が逆だと、要求したフレームが古い値を読みます。

### なぜ setState ではいけないのか

`setState(fn)` は `fn` を**呼び出し元のタスクで即座に実行**します。したがって:

1. **ビルドと競合します。** UI タスクが `build()` でそのメンバを読んでいる最中に書き換わります。
   `int` なら値が壊れるだけですが、`std::string` や `std::vector` のメンバなら use-after-free です。
2. **`fmt()` や `Str` がアリーナを壊します。** `Arena::current()` はグローバルで、UI タスクが
   使用中のものを指しています。このコードベースで文字列を作る標準的な書き方が `fmt()` なので、
   **これは「うっかり」で起きます。**症状は無言のメモリ破壊です。

どちらも単一タスクのデモでは絶対に踏みません。**「動いているように見える」ことが、この問題の本体です。**

そこで `Element::markNeedsBuild()` に**アサート**を置いてあります。`FmsApp` は最初のフレームで
自分のスレッドを記録し、違うスレッドから来たら即座に落とします。無言の破壊を、位置つきの
アサートに変えるためのものです(ユニットテストはツリーを直接叩いてフレームループを持たないので、
スレッドが記録されず、この検査は無効のまま通ります)。

#### スレッドの識別子はプラットフォームが渡す

**`std::this_thread::get_id()` は実機で使えません。** ESP-IDF ではこれが `pthread_self()` を
呼び、**pthread として作られていない FreeRTOS タスクから呼ばれると assert して落ちます** ——
そしてフレームループが走るのは `esp_lvgl_port` が作る素の FreeRTOS タスクです。最初にこれを
入れたときは実機が**最初のフレームでリブートループ**しました。ビルドは通っていたので、
コンパイルの成功を動作確認と読み違えたのが原因です。

なので識別子は、マイクロ秒クロックと同じく**プラットフォームから注入**します:

```cpp
using ThreadId = uintptr_t;                      // 比較しかしない
FmsApp::instance().setThreadId(thread_id);       // 最初のフレームより前に
```

| | 渡すもの |
|---|---|
| 実機 | `(ThreadId)xTaskGetCurrentTaskHandle()` |
| シム / ホストテスト | `std::hash<std::thread::id>{}(std::this_thread::get_id())` |
| 未設定 | **検査ごと無効**(bind もせず、関数も呼ばない) |

最後の行が要点です。**診断機能が仕事を止めてはいけない** —— 答え方を教わっていないときに
推測すると、まさに上のリブートループになります。この「未設定なら何も呼ばない」は
`test_without_a_thread_id_the_check_is_off` で押さえてあります。

これで `components/fmsui` は ESP-IDF に依存しないまま、実機でだけ意味のある識別子を使えます。

### requestFrame() が安全な理由

`BuildOwner::needs_build_` は `std::atomic<bool>` で、`scheduleBuild()` は release ストア 1 回です。
**確保も、ロックも、ブロックもしません。** 100Hz のセンサが毎サンプル呼んでも、UI を待つことは
ありません。上の単一 producer の例では、UI の `takeNeedsBuild()` がその要求を acquire したとき、
release/acquire の対によって、要求前の `altitude_` への書き込みがその後のビルドから見えます。

ただし、複数 producer が同じ要求フラグへ `true` を書いた場合、UI の 1 回の acquire がすべての
producer の release と同期するわけではありません。要求フラグはデータ配送路ではなく、あくまで
ビルドのスケジュールと集約のためのものです。複数 producer が公開する各データは、それ自体を atomic
にするか、ロック、キュー、不変オブジェクトの受け渡しなどで個別に同期してください。

**値をキューに積まない**のが要点です。要求は「入力を読み直せ」としか言わないので、UI は
最新値を 1 つ描きます。100 個の古い更新を順に再生するのは、ストリーミングデータに対して
やりたいことではありません。

フレーム中に届いた要求も失われません。`takeNeedsBuild()` は exchange なので、ビルド中に立った
フラグは次のフレームが拾います。

この性質は `tests/fmsui_request_frame_test.cpp` が負荷の下で押さえています。対象は、停止中の burst、
ビルド中の要求、単一 producer と複数 producer の継続更新、停止後の収束です。複数 producer の
ケースでは公開値も producer ごとの世代も atomic にしており、要求フラグが全 producer のデータを
公開できることを検査しているわけではありません。**要求回数とビルド回数の一致は検査しません。**
集約こそが意図した動作だからです。代わりに、ビルド回数が要求回数を超えないこと、読んだ値が
逆戻りしないこと、最後に公開された値が画面まで届くこと、その後の idle frame でビルドしないことを見ます。

### ISR から

**推奨しません。** ESP-IDF の定石どおり、ISR はタスクに通知し、そのタスクから `requestFrame()`
を呼んでください。ISR がフラグを立てるだけでは何も進みません —— 受け取ったデータを、ビルドが
読める場所へ置く仕事が残るからです。

どうしても IRAM の ISR から直接叩く必要がある場合のために、`FmsApp::requester()` があります。
`FmsApp::instance()` は**フラッシュ上の関数**なので、`ESP_INTR_FLAG_IRAM` 付きのハンドラからは
呼べません(実行中はフラッシュキャッシュが無効になり得ます)。`FrameRequester` はフラグへの
ポインタだけを持ち、`request()` は呼び出し側にインライン展開される release ストア 1 回です。
セットアップ時に 1 つ取って、ハンドラから届く場所に置いておいてください。

### 統計は「1 フレーム分」をまとめて渡す

計測値も、書くのと読むのが別タスクです。フレームループが書き、ログを出す側が読みます。
`FmsApp::stats()` が**参照ではなくコピー**を返すのはそのためです。参照を渡すと、読み手が
フィールドを 1 つずつ舐めている最中に次のフレームが書き込み、**build はこのフレーム、paint は
次のフレーム**という合計の合わない値が取れます。もっともらしく見えて、どのフレームも
表していない数字です。

**フィールドごとに atomic にする方法は採りません。**個々の読み書きが安全になるだけで、
混ざること自体は防げないからです。atomic にすべき単位は構造体全体なので:

- フレームループは 1 フレーム分をローカルの `FrameStats` に組み立てきる
- 最後に短いロックの中で、公開用のコピーへ 1 回代入する
- `stats()` は同じロックの中でコピーを返し、ログ出力はロックの外で行う
- 累積の `builds` はフレームループだけが持つメンバで、完成したコピーに載せて渡す

ロックの中にビルドもレイアウトも描画もログもありません。**小さな構造体のコピー 1 回だけ**です。

LVGL 自身の再描画時間(`LV_EVENT_REFR_START` → `REFR_READY`)も同じ形にしてあります。
`fmsui::RefreshStats` がカウンタを所有し、`take()` が「前回の `take()` からの回数・合計・最大」を
**まとめて 1 回で**返して次の区間を始めます。`volatile` を並べて読み手が個別にサンプルし、
最大値だけ別途ゼロクリアする —— という以前の形では、`avg` が「この秒のマイクロ秒 ÷ 次の秒の回数」に
なり得ました。`volatile` はそもそも同期の道具ではなく、C++20 では複合代入が非推奨で
実機ビルドに警告も出ていました。

### まだ無いもの

**非 atomic な状態を他タスクから触る経路**はありません。`FmsApp::post(fn)` のような
「UI タスクで実行する関数をキューする」仕組みは、必要になってから入れます。いまのところ
「同期された値を publish して requestFrame」で足ります。

## テーマ (M2)

`FmsTheme::of(ctx)` で色とフォントを木の下に流します。**Flutter の InheritedWidget より遥かに単純で、
それは全体再ビルドのおかげです。** Flutter は「どの Element がどの InheritedWidget を読んだか」を
追跡して、値が変わったときにその Element だけを再ビルドする必要があります。我々は何か変われば
全部再ビルドするので、**追跡も通知も要りません**。`of()` は Element の親を辿るだけです。

色の名前は**意味**であって見た目ではありません。実機の Airbus FMS では色そのものが意味だからです:
シアンはパイロットが入力してよい値、緑はシステムが計算した値、アンバーは注意、マゼンタは制約。
フィールド名を `cyan` にすると、間違った理由でその色を選べてしまいます。

```cpp
const FmsThemeData &t = FmsTheme::of(ctx);
new Text{{ .text = "153", .font = t.font.value, .color = t.color.entry }}   // entry = 入力可能
```

`FmsTheme` は lv_obj を 1 つも作りません(実測: テーマ導入前後で lv_objs は 34 のまま)。

## フォント (M2)

**B612 Mono** に決定。Airbus が ENAC と共同で、コックピット表示のために Intactile DESIGN に
作らせた書体。SIL OFL 1.1。候補4種(B612 Mono / JetBrains Mono / IBM Plex Mono / Martian Mono)を
同じ FMS 画面・同じ色・同じサイズで並べて比較した上での判断。

決め手は **字幅の細さ**でした。FMS のページは横方向に情報を詰め込むので、1 文字の幅がそのまま
1 行に載る情報量になります。B612 が 4 つの中で最も細く、参考画像の見た目にも最も近い。

**既知の弱点**: ゼロに点も斜線もなく、`0` と `O` は字幅だけで区別します。実機の A350 も
プレーンなゼロなので実態には忠実ですが、安全上の性質としては弱い。必要になれば OFL は改変を
許可しているので、ゼロのグリフだけ差し替えて再ラスタライズできます。

ビットマップ化(`tools/gen_fonts.py` → lv_font_conv)で 16/20/24/28/32px、4bpp。
ランタイム FreeType ではなくビットマップなのは、グリフ集合が固定で小さく、サイズも既知で、
描画時に CPU もヒープも消費しないためです。

**▼ や矢印はフォントに入れていません。** B612 にグリフが無いこともありますが、そもそもそれらは
テキストではなく UI の部品です。M3 で図形として描くので、ウィジェットと一緒に拡縮・着色されます。

## FMS ウィジェット (M3)

`FmsScaffold` / `FmsPanel` / `FmsTabs` / `FmsFieldBox` / `FmsButton` / `FmsDropdown` / `FmsRadio` /
`FmsDivider` / `FmsScratchpad` / `FmsKeypad`。**すべて StatelessWidget で、プリミティブの合成**です。
新しい RenderObject を足したのは 1 つだけ:

### CustomPaint — 矩形で作れない形のために

台形のタブ、ドロップダウンの ▼、ラジオのドット。これらは矩形の組み合わせでは作れません。
`CustomPaint` は LVGL の `LV_EVENT_DRAW_MAIN` にフックして、ウィジェット座標系の `Canvas`
(`fillRect` / `line` / `polygon` / `circle`)を渡します。

**フォントのグリフとして持ち込まない**のが要点です。図形として描けば、ウィジェットと一緒に拡縮・着色され、
どのフォントを選べるかを縛りません(B612 Mono には U+25BC が無い)。

### 色は役割で選ぶ

`FmsRole` は `Entry` / `Computed` / `Attention` / `Constraint` / `Label`。実機の FMS では色が意味なので、
呼ぶ側は「シアン」ではなく「パイロットが入力してよい値」を選びます。

### スクラッチパッド

実機の MCDU と同じで、**先に打ってから、どこに入れるかを指す**。`FmsKeypad` が
`FmsScratchpad` に文字を積み、フィールドをタップするとそこへ確定します。空のまま確定しようとすると
アンバーで `SCRATCHPAD EMPTY`。

## ツリーの形を変えると全部作り直される (M4 で踏んだ)

キーパッドをモーダルで開くとき、最初はこう書きました:

```cpp
if (editing_ == nullptr) return pages;          // Row
return new Stack{{ .children = { pages, scrim, keypad } }};
```

**キーパッドを開くたびに 600ms かかりました。**

ルートの Widget 型が `Row` から `Stack` に変わると Element の同一性が失われます。差分検出は
「型が違う = 別物」と判断してサブツリーを丸ごと捨てるので、**lv_obj 282 個が全部破棄されて作り直され**ました。

直し方は、ツリーの形を常に同じにすること:

```cpp
std::vector<Widget *> layers = { pages };       // 常に Stack
if (editing_) { layers.push_back(scrim); layers.push_back(keypad); }
return new Stack{{ .children = WidgetList(layers.data(), layers.size()) }};
```

`children[0]` がどちらの状態でも同じ `Row` なので、ページ側は Element を保ち、増減するのは
オーバーレイの 2 つだけになります。**600ms → 106ms。**

教訓は **「木の形は固定して、葉を変える」**。Flutter でも同じ理由で同じ規則が効きます。

## 性能 (M5)

実機で測って、直して、また測りました。**失敗した実験も含めて** [PERF.md](PERF.md) に全部書いてあります。

要点だけ:

- **テキスト測定のキャッシュ** で layout が 8.2ms → 2.1ms。毎回すべてのラベルを測り直していました。
- **共有 `lv_style_t`** で lv_obj の生成が 1.85ms → 1.0ms。`lv_obj_set_style_*` はプロパティを
  1 つ足すたびに realloc し、その配列は PSRAM 上にあります。UI はオブジェクトが多くても
  見た目の種類は少ないので、組み合わせごとに 1 個作って共有すれば済みます。
- **アリーナを内部 SRAM に移す実験は失敗**しました。全部遅くなりました。内部 SRAM は 200KB しかなく
  すでに有効に使われていて、アリーナが 64KB 奪うと Element も RenderObject も LVGL オブジェクトも
  PSRAM に押し出されたからです。

**再ビルドはフレームごとには起きません。** `setState` のときだけです。したがって 18ms は
1 操作あたりの一回きりのコストで、33ms のフレーム予算に収まります。だから
dirty サブツリー再ビルドはまだ実装していません — **必要が無いことを実測が示しているから**です。

### スタイルキャッシュは LVGL セッションの寿命で持つ

共有 `lv_style_t` は**一度作ったら追い出しません**。`lv_obj` はスタイルを**コピーせず生ポインタで
持つ**ので、LRU で 1 つ捨てれば画面に出ている側が解放済みメモリを読みます。そして追い出す理由も
ありません —— 色・フォント・配置・枠線・角丸はテーマと画面設計から来るので**種類は有限**で、
件数は頭打ちになります。毎フレーム新しい色や角丸を作る使い方、スタイルの連続アニメーションは
この前提の外です。

上限を先に決めて切り捨てるのではなく、**測ります**。`fmsui::styleCacheStats()` が text / box の
件数を返し、追い出しが無いので**それがそのままセッション中の最大到達数**です(だから件数と最大値の
2 つは持ちません。同じ数だからです)。件数はベクタを別タスクから直接読まず、UI タスクが
スタイル追加後に公開用スナップショットへコピーします。診断タスクはそのコピーだけを短いロック内で
読むため、新しいスタイルを初めて描画している最中でも `vector::size()` と `push_back()` は競合しません。
実測:

| 画面 | lv_objs | text スタイル | box スタイル |
|---|---|---|---|
| `--demo catalog` | 124 | 13 | 5 |
| `--demo pages` | 252 | 9 | 5 |

252 個のオブジェクトに対して 14 種類。**これがキャッシュが成立している理由**で、タップを
繰り返しても増えません(`test_repeating_a_style_set_does_not_grow_the_cache`)。

`test_frame_and_style_stats_are_safe_to_read_during_frames` は、UI 側で 32 種類のスタイルを
初めて描画し続ける間、別スレッドからフレーム統計とスタイル件数を読み続けます。
`test_refresh_stats_take_a_consistent_interval` は、リフレッシュ完了と別スレッドからの `take()` を
並行させ、回数・合計・最大が同じ区間の値であることを確認します。

所有者は `render.cpp` 内の `StyleCache` で、エントリを 1 個ずつヒープに置きます
(ベクタが伸びても `&style` が動かないように)。実機ではアプリケーション存続中の常駐キャッシュです。
シムとテストは `FmsApp::shutdown()` で終わらせます —— **タイマ停止 → Element ツリー破棄
(= `lv_obj` も破棄)→ スタイル解放**の順で、これを逆にすると解放済みスタイルを指したまま
オブジェクトが残ります。この順序があるので LeakSanitizer 下の `fmsui_test` と
`fmsui_sim --shot` はスタイル由来の報告を出しません。

## 実装上のはまりどころ

### C++20 の指定初期化子は宣言順を守る必要がある

```cpp
new Container{{ .color = kBg, .padding = ... }}   // コンパイルエラー
new Container{{ .padding = ..., .color = kBg }}   // OK(構造体の宣言順)
```

Flutter の名前付き引数と違い、順序が自由ではありません。これは C++ の制約で回避できません。
Args 構造体のフィールド順は、使う側が書きたい順(外側→内側、レイアウト→装飾→child)に並べています。

### Widget 以外を `new` してはいけない

`ContainerArgs` の `alignment` は当初 `Alignment*` にしていましたが、`new Alignment(...)` は
グローバルの `operator new` を呼ぶのでリークします。アリーナが所有するのは Widget だけです。
「未設定」を表すのに NaN をセンチネルとして使っています。

### コメントで守らせる API は間違い

`WidgetList` に「実行時に長さが決まるリスト」用のコンストラクタを足したとき、最初は
**コピーせずポインタを受け取る**設計にしました。「アリーナのメモリを渡すこと」とコメントも書きました。

最初の呼び出し側(`FmsKeypad`)が**スタック配列**を渡し、segfault しました。

コピーする実装に変えて、罠自体を消しました。コストは無視できる大きさで、呼ぶ側は
`std::vector` をそのまま渡せるようになり、コメントも要らなくなりました。

### 境界ちょうどに引いた線は消える

タブの上辺を `y=0` に、右辺を `x=width` に引いたら、線幅 1 の半分がオブジェクトの外に出て
LVGL にクリップされ、**タブが枠を失いました**。ストロークの半分だけ内側に寄せる必要があります。

### 装飾は touch を吸ってはいけない

`lv_obj_create()` はデフォルトで `LV_OBJ_FLAG_CLICKABLE` を立てます。そのままだと `Container` の枠が
その下の `GestureDetector` に届くはずのタッチを飲み込みます。描画専用のオブジェクトからは
CLICKABLE と SCROLLABLE を必ず落としています(`makeInert()`)。
