# 性能 — 実機で測ったこと

対象: M5Stack Tab5 (ESP32-P4 rev v1.0, 360MHz, PSRAM 32MB HEX 200MHz), ESP-IDF 5.5.4, LVGL 9.5.0。
画面は `ACTIVE/PERF` + `ACTIVE/INIT` の 2 面(Widget 740 / lv_obj 238)。

## まず「いつ」コストが発生するかを正しく理解する

**再ビルドはフレームごとには起きません。** `setState` が呼ばれたときだけです。FMS の画面は
触られなければ静止しているので、**再ビルドのコストは 1 操作あたりの一回きり**であって、
毎フレームの負担ではありません。

30fps のフレーム予算は 33ms。1 操作で 18ms なら、最悪でも 1 フレーム落ちるだけです。

## 内訳(最適化後)

| | build | layout | paint | 合計 |
|---|---|---|---|---|
| 通常の再ビルド | 15.4 ms | 2.1 ms | 0.6 ms | **18.1 ms** |
| キーパッドを開く(lv_obj を 54 個生成) | 12.0 ms | 2.5 ms | 54.5 ms | **69 ms** |

LVGL 自身のリフレッシュは、部分再描画で平均 **0.2ms** / 最大 2ms、**29 refr/s**(LVGL の
`LV_DEF_REFR_PERIOD=33` の上限に張り付き)。起動時の全画面 1 回だけ 43ms。

## 並べ替えのコスト(シミュレータ実測 + 実機への外挿)

キー付き再配置を入れたとき、心配したのは再突合そのものではなく **`lv_obj_move_to_index`** でした。
lv_obj ツリーはフラットで 1 画面に 200〜300 個が同じ親にぶら下がっているので、1 個を動かすと
他の index がずれ、大きな並べ替えでは付け替えが積み上がります。

`--demo reorder --rows 40 --stats` で測りました。**40 レグ = lv_obj 301 個**で、実機ページの
238 個と同規模です。数字はシミュレータ(Release, WSL)の中央値:

| 操作 | build | layout | paint | lv_created |
|---|---|---|---|---|
| 並べ替えなしの再ビルド | 95 µs | 23 µs | **110 µs** | 0 |
| 隣接 1 つ入れ替え(MOVE DOWN) | 110 µs | 21 µs | **190 µs** | 0 |
| 全反転(全 lv_obj の index が変わる) | 125 µs | 32 µs | **3 580 µs** | 0 |

読み取れること:

1. **再突合(build)は並べ替えの規模に関係なく一定**です。95 → 125µs しか動きません。
   キー付きの引き取りは、コストとしては見えません。
2. **コストは全部 paint、つまり `lv_obj_move_to_index`** です。全反転で通常の再ビルドの **33 倍**。
3. **`lv_created` は 0** —— 300 個の lv_obj を 1 つも作り直さずに並べ替えています。これがキーの効果です。
4. **リストが長くなると、オブジェクト数より速く増えます。** レグ数を振ると paint の中央値は
   133 個 1.0ms → 245 個 2.4ms → 301 個 3.6ms → 469 個 8.0ms → 917 個 21.6ms → 1813 個 48.3ms。
   1 オブジェクトあたり 7.8µs → 26.6µs で、線形ではありません(指数はおよそ n^1.3〜n^1.8)。
   フラットな親の中で index を動かす以上、これは避けられません。

### 実機に載せて測った(シム→実機の比)

`idf.py -DFMSUI_DEMO=reorder -DFMSUI_ROWS=40 build` を Tab5 に書き込んで、同じ画面を両方で測りました。
lv_obj は実機でもシムでも **301 個 / Widget 781 個**で一致します。並べ替えなしの再ビルド:

| | シミュレータ | 実機 | 比 |
|---|---|---|---|
| build | 95 µs | 2 400 µs | 25× |
| layout | 23 µs | 600 µs | 26× |
| paint | 110 µs | 2 290 µs | 21× |
| 合計 | 240 µs | **5 300 µs** | 22× |

**3 フェーズとも一様に 20〜26 倍**でした。当初 paint だけ 6 倍と見積もっていましたが、これは
下の「通常の再ビルド」表(paint 0.6ms)を基準にしたためで、**誤りです**。

### 全反転を実機で測った: paint 127.6ms

実機の REVERSE を押して取った値です。

| | シミュレータ | 実機 | 比 |
|---|---|---|---|
| 並べ替えなしの paint | 110 µs | 2 290 µs | 21× |
| **全反転の paint** | **3 580 µs** | **127 596 µs** | **35.6×** |

**33ms の予算に対して約 4 倍**。合計 130ms で、4 フレーム分落ちます。

比が一様ではない、というのがここでの学びです。並べ替えなしの paint は 21 倍なのに、全反転は
35.6 倍。`lv_obj_set_pos` がフィールドを 2 つ書くだけなのに対し、`lv_obj_move_to_index` は
親の子ポインタ配列を memmove し、さらに 301 個ぶんの invalidate が走ります。どちらも PSRAM 上の
話なので、実機のほうが不利の度合いが大きく出ます。

**21 倍を当てて 75ms と見積もっていましたが、実測は 1.7 倍悪い 127.6ms でした。**
フェーズごとの比を、性質の違う操作にそのまま流用してはいけない、という例です。

もし最適化するなら、まず疑うべきは `move_to_index` そのものより **invalidate の側**です。
301 個を個別に invalidate すると LVGL の dirty area バッファ(`LV_INV_BUF_SIZE`、既定 32)が
溢れて全画面無効化に落ち、領域の結合も効かなくなります。**未検証の見立て**なので、手を付ける前に
`lv_obj_invalidate` を潰した版で測って切り分けてください。

### 隣接入れ替えも測った: paint 6.4ms 、そして線形だった

実機の MOVE DOWN を押した値です。これで両端が揃いました。

| 操作 | `lv_moved` | シム paint | 実機 paint | 実機の増分 / 1 個 |
|---|---|---|---|---|
| 並べ替えなし | 0 | 110 µs | 2 290 µs | — |
| 隣接入れ替え | 7 | 190 µs | **6 372 µs** | 583 µs |
| 全反転 | 273 | 3 580 µs | **127 596 µs** | 459 µs |

**1 個あたりおよそ 0.5ms**(460〜580µs)。目安としては:

```
実機の paint ≒ 2.3ms + 0.5ms × lv_moved
```

**33ms に収まるのは 1 フレームあたり 60 個前後まで**。ウェイポイントを 1 つ上下に動かすのは
7 個なので十分内側、リスト全体の並べ替えは 273 個で 4 倍超過です。

1 個あたりの単価が大きい移動(583µs)のほうが**少数の**移動だという点は、直感と逆です。273 個
動かすと LVGL の dirty area バッファ(`LV_INV_BUF_SIZE`、既定 32)が溢れて全画面 1 枚の無効化に
落ちるのに対し、7 個なら 7 領域を個別に結合するため —— という説明が考えられますが、**未検証**です。

#### この表は一度間違えています

最初は移動数を木の構造から**推定**して 14 個 / 280 個と書き、1 個あたり 455µs と 456µs が
一致したので「きれいに線形」と結論しました。その後 `FrameStats::lv_moved` を足して**実測**したら
**7 個 / 273 個**で、単価も 583 と 459 に割れました。**一致は推定値の偶然**だったわけです。
数えられるものを推定して、一致したことを裏付けと読んだのが誤りでした。

### 操作の性質で比が変わる(まとめ)

| | シム→実機の比 |
|---|---|
| index を動かさないフレーム | 21× |
| index を動かすフレーム | 34× (33.5 と 35.6) |

`lv_obj_set_pos` はフィールドを 2 つ書くだけ、`lv_obj_move_to_index` は親の子ポインタ配列を
memmove して invalidate を起こす —— PSRAM 上ではこの差が開きます。**フェーズ単位の比を
操作単位に流用しない**こと。全反転を 21 倍で見積もって 75ms と書き、実測 127.6ms で 1.7 倍
外したのがその失敗例です。

### 上の「通常の再ビルド」との食い違いを切り分けた

`-DFMSUI_DEMO=pages` を実機に焼いて、同じ画面を測り直しました。

| | Widget | lv_obj | build | layout | paint | 合計 |
|---|---|---|---|---|---|---|
| 上の表(記載) | 740 | 238 | 15.4 ms | 2.1 ms | 0.6 ms | 18.1 ms |
| **pages 実測** | 780 | 252 | **5.75 ms** | **2.27 ms** | **3.41 ms** | **11.4 ms** |
| reorder 実測 | 781 | 301 | 2.4 ms | 0.6 ms | 2.29 ms | 5.3 ms |

**build の 6 倍差は、原因が 2 つ重なっていました。**

1. **上の表の build が古い。** 同じ画面で 15.4ms → 5.75ms。layout は 2.1 → 2.27ms でほぼ一致
   するので、表全体が古いのではなく build だけが変わっています。
2. **ページごとに Widget 1 個の重さが違う。** pages と reorder は Widget 数がほぼ同じ
   (780 対 781)なのに build は **5.75ms 対 2.4ms で 2.4 倍**。FMS ページの Widget は
   `std::function` のキャプチャと `fmt()` が桁違いに多く、その差がそのまま出ます。

**したがって Widget 数から build 時間は見積もれません。** 画面ごとに測ってください。

### 保留: pages の paint が 0.6ms → 3.41ms

同じ画面で paint だけが 5.7 倍に増えています。**急がないので保留にしています** —— 現状 33ms の
予算内(合計 11.4ms)に収まっており、何もブロックしていません。再開する人向けに、分かっていることを
書き残します。

**排除済み — キー付き再配置ではありません。** シミュレータで pages を測ると `lv_moved` が 0 で、
paint も 27〜83µs しかかかりません(reorder の全反転は `lv_moved=273` / 3 137µs)。z 順の
付け替えは起きておらず、再突合は paint フェーズに一切触れていません。build が同じ画面で
15.4 → 5.75ms と**速く**なっていることも、全体的な劣化ではないことを示しています。

**残る候補。**

- (a) 上の表の paint が別の版・別の設定で測られた
- (b) pages 自体が育った(740 → 780 Widget、238 → 252 lv_obj)。とくに **CustomPaint を使う
  widget**(斜めタブ、ドロップダウンの三角、ラジオの丸)は `lv_event` の描画コールバックを持ち、
  素の lv_obj より paint が重い可能性がある

**決着させるには。** (b) なら、CustomPaint の数と paint 時間の関係を測れば分かります —— タブや
ラジオを一時的に素の矩形に差し替えて実機で測り、paint が落ちるかを見るのが最短です。
(a) を追うには履歴が要ります。**このリポジトリにはコミットが 1 つも無く、「いつ変わったか」を
追う手段がありません。** 最初のコミットを打っておくことが、この種の問いに答える前提条件です。

## 効いた最適化

### 1. テキスト測定のキャッシュ — layout 8.2ms → 2.1ms

`RenderText::performLayout` が毎回 `lv_text_get_size()` を呼んでいました。これは文字列を歩いて
グリフ幅を足す処理で、レイアウトは再ビルドのたびに木全体を走ります。150 個のラベルが、
**変わっていない答えを毎回計算し直していた**わけです。

テキスト・フォント・幅の制約が動いたときだけ測り直すようにしました。

### 2. 共有スタイル — lv_obj の生成 1.85ms → 1.0ms

`lv_obj_set_style_*()` はオブジェクトの**ローカルスタイル**に書き込み、LVGL はその
プロパティ配列を 1 個ずつ realloc します。新しいオブジェクトに 6 個セットすれば 6 回の realloc、
しかも LVGL のヒープは PSRAM 上です。

UI はオブジェクトが多くても**見た目の種類は少ない**。このページはラベルが 150 個ありますが、
(フォント, 色, 揃え)の組み合わせは十数種類しかありません。組み合わせごとに `lv_style_t` を
一度だけ作って共有すれば、realloc の列が `lv_obj_add_style()` 1 回になります。

あわせて `makeInert()` の `lv_obj_set_style_pad_all(o, 0, 0)` を削除しました。
`lv_obj_remove_style_all()` の後はデフォルト値(= 0)が効くので、**何も変えないために
プロパティを 4 つ足していた**ことになります。

### 3. 差分検出のアロケーション削除

`setChildren()` が再ビルドのたびに子リストの `std::vector` を作り直してコピーしていました。
比較して、変わっていなければ何もしないようにしました。効果は 1ms 未満で、期待したほどでは
ありませんでした。

## 失敗した実験:アリーナを内部 SRAM に置く

ESP-IDF は `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`(既定 16KB)を超える確保を PSRAM に回します。
アリーナのチャンクは 32KB なので、**Widget ツリー全体が毎フレーム PSRAM に書かれている**ことになります。
これが build 15ms の原因だと考え、`heap_caps_malloc(MALLOC_CAP_INTERNAL)` に切り替えました。

**全部遅くなりました。**

| | 変更前 | 変更後 |
|---|---|---|
| build | 15.3 ms | 26.0 ms |
| layout | 2.0 ms | 3.8 ms |
| paint | 0.6 ms | 2.2 ms |

理由は明白です。内部 SRAM は 200KB しかなく、**すでに有効に使われていました**。アリーナが 64KB を
奪ったことで、それまで内部に収まっていた Element、RenderObject、そして LVGL 自身のオブジェクトが
PSRAM に押し出されたのです。

アリーナは問題ではなく、**内部 SRAM は我々が取ってよい資源ではありませんでした**。差し戻し済みです。

## 残っているもの: build 15.4ms

Widget 1 個あたり約 21µs。360MHz で 7500 サイクルです。バンプ確保とコンストラクタにしては多すぎ、
実体は **PSRAM へのランダムアクセスによるキャッシュミス**です。内部 SRAM には収まりません(上記)。

本質的な解は **dirty サブツリーだけを再ビルドすること**で、それは
[DESIGN.md](DESIGN.md) に書いた移行先そのものです(Element に Widget のコピーを所有させる)。

**いま実装しないのは、必要が無いからです。** 18ms は 33ms の予算に収まり、しかも操作ごとに一度きり。
測ってから決める、を守っています。

## チューニングしなかったもの、とその理由

- **描画バッファサイズ** (`BSP_LCD_DRAW_BUF_HEIGHT`): 50 行(720×50×2 = 72KB × 2 枚、内部 SRAM)。
  部分再描画のリフレッシュが平均 0.2ms しかかかっておらず、**そもそもボトルネックではありません**。
  100 行にすると 2 枚目が内部 SRAM に入らず `bsp_display_start()` が assert します。
- **CPU 400MHz**: P4 は 400MHz まで上げられますが、M5 自身のファームウェアが 360MHz を選んでいます。
  11% のために PSRAM タイミングの安定性を賭ける価値はないと判断しました。
- **LVGL 9.4+ の PPA 描画ユニット**: 回転はすでに PPA でハード処理されており、描画そのものは
  ボトルネックではありません(paint 0.6ms)。experimental でティアリングの既知不具合もあります。
